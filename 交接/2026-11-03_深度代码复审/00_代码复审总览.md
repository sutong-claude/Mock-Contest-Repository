## 1. 最严重的发现：独立验证器自身有「共模假绿」风险

`考古/验证脚本/verify_codelands3_candidates.py`（78 行）的 `covered()` 与被测 C++ 候选 `CodeLands3_maxcover_二维树状数组.cpp` **共用同一个分解**：

```
dp[i] = max( dp[i-1], i + max_{t<i, sa[t]<=sa[i], sb[t]<=sb[i]} (dp[t]-t) )
```

v1 只是把「支配查询」换成 O(n²) 逐段求和，属于**同一数学模型的不同实现**，不是独立真值。这恰是仓库 `2026-10-02_CSP-S模拟赛day4/原始材料/T2_对拍污染链_非法generator_错oracle.md` 用 50,069 个合法输入证明过的陷阱：generator / oracle / candidate 三层同源时，`diff` 相等不代表对。

**本轮处置**：写 [`verify_codelands3_candidates_v2.py`](../../考古/验证脚本/verify_codelands3_candidates_v2.py)，加入**完全独立**的两个 oracle：

- maxcover：`brute_segments(a,b)` 递归枚举所有两两不相交合法段集合，**不用 DP、不用前缀和、不用支配关系**；
- alien：`brute_permanent(N,n)` 用子集 DP 数 0-1 矩阵 permanent，与容斥公式 `Σ(-1)^k C(n,k)(N-k)!` 完全独立。

v2 实测输出（结构化 JSON，可复算）：

```
CODELANDS3_V2_PASS
  maxcover_exhaustive_python_triples = 597,870   # n<=6, {-1,0,1}^n × (a,b) 全空间
  maxcover_cpp_vs_brute_cases        = 402       # C++ 二进制 vs 真穷举
  maxcover_adversarial_cases         = 2,000     # 全0 / ±1 / 相等前缀 / 大随机数
  maxcover_sanitizer_runs            = 40        # ASAN+UBSAN 0 报错
  maxcover_large_n_analytic          = all_zero 200000 / all_neg 0 / single_pos_then_neg 1
  alien_permanent_cases              = 66        # N<=10 全 (n,m) 组合
  alien_large_N_crosscheck           = 5 组（最大 n=1234,m=4321）
```

**结论**：v1 的 `covered()` 在 597,870 组小空间上与真穷举**完全一致**，所以 v1 的 602 次通过不是假绿；但这是**本轮补证后才敢下的结论**，v1 自己无法给出。这正是「验证器也要被验证」。

## 2. 真 bug：Day1 A 的 `distance(multiset...)` 是 O(n³)

`2026-09-25_CSP-S模拟赛day1/赛时代码/A_v4_n方multiset_已提交_21-10.cpp:23,35,38`：

```cpp
int num = distance (st1.upper_bound(a[i]), st1.end());
```

`std::multiset` 是**双向迭代器**，`std::distance` 必须逐节点 ++ → **单次 O(n)**；它在 `for i=1..n` × `for j=i+1..n` 双重循环里被调用两次 → **O(n³)**。仓库 `错因档案.md` 只写了「在 multiset 上用 distance 是 O(n)」，本轮把它量化并改写。

### 2.1 改写版

[`Day1A_改写_树状数组版.cpp`](Day1A_改写_树状数组版.cpp)：坐标压缩 + Fenwick 前缀计数，把每次查询降到 O(log n)，整体 **O(n³) → O(n² log n)**；同时修掉三个工程隐患：

1. **删掉 `#define int long long`**：全仓 **136/170** 份 C++ 带这个宏，且 **136 份全部靠 `signed main()`** 规避（因为宏下 `int main()` 是硬错误，实测 `cc1plus: error: '::main' must return 'int'`）。副作用：所有 `int` 数组/容器翻倍为 8 字节，且若把 `scanf("%d", &x)` 抄进来就是 UB。
2. **坐标压缩**：旧 `正解代码/A_记录带_赛时代码只换树状数组.cpp` 直接 `add(a[i])` 并循环到 `n`，**隐含假设 `a_i ∈ [1,n]`**；改写版支持任意 `long long` 值、重复值与负数。
3. **显式 64 位累加**：`ans/tot/x/y` 用 `long long`，避免 n 大时溢出。

### 2.2 等价性与基准（`基准与等价性.py`，实测）

| 验证项 | 结果 |
| --- | --- |
| n=1..6 全排列（873 组）三版输出 | `multiset == bit == rewrite` ✅ |
| 含重复值 / `a_i > n` / 负数（400 组） | `multiset == rewrite` ✅（旧 bit 版因越界退出对比） |
| n=100 | multiset 0.0033s / rewrite 0.0008s → **4.1×** |
| n=200 | multiset 0.0160s / rewrite 0.0010s → **16.0×** |
| n=400 | multiset 0.0797s / rewrite 0.0022s → **36.2×** |
| n=800 / 1600（rewrite） | 0.0115s / 0.0822s |

计时方法：一次进程内喂 5 组相同数据、取 2 轮最小值再除以 5，消除 `fork+exec` 启动噪声（早期版本直接测单次进程，得到 2.1/6.4/24.3×，被启动开销压低；本轮以 `基准与等价性.py` 的输出为准）。两次重复运行 n=100/200 的加速比约 3.7~4.1× / 14.7~16.0×，n=400 稳定 36.2×。multiset 耗时 0.0033→0.0160→0.0797 约 **4.8~5.0×/倍增**，与 O(n³) 的 8× 上界之间差一个 `std::distance` 常数，符合 O(n³) 增长；rewrite 800→1600 约 7.1×，符合 O(n² log n)。

### 2.3 不吹牛的边界：剩下 O(n²) 没有降到 O(n log n)

把目标函数化简可得恒等式（`x+y = C(len,2)`）：

```
now(i,j) = ans + C(j-i+1, 2) - 2·inv(i,j)
```

其中 `inv(i,j)` 是子段内逆序对数。令 `s(k,l)=+1`（非逆序）/`-1`（逆序），问题是求

```
max_{i<=j} Σ_{i<=k<l<=j} s(k,l)
```

这是**二维（三角阵）最大子段和**，不是一维最大子段和：递推 `f(i,j)=f(i,j-1)+Σ_{k=i}^{j-1}s(k,j)` 对每个 j 仍需 O(n) 个 i。要突破 O(n²) 需要分治 + 决策单调性/支配结构的专门设计，本轮**不声称已做到**，也不拿「换树状数组」冒充复杂度转换。这呼应 `错因总表` #16「正确朴素模型没有触发复杂度转换」——但 Day1 A 的教训首先是 **STL 迭代器复杂度盲区（#2）**，两者不能混为一谈。

## 3. 真 bug：Day7 A 用 200 万个空 `priority_queue` 撑爆内存

`2026-10-06_CSP-S模拟赛day7/赛时代码/A_兄弟.cpp:7-8`：

```cpp
priority_queue <int> p1[1000010];
priority_queue <int, vector <int>, greater <int>> p2[1000010];
```

2,000,020 个 `priority_queue` 对象，每个内含一个 `vector`（24 B）+ 比较器（补齐后 ≥32 B）→ **约 64 MB 纯空容器**，且构造期要做 200 万次对象初始化。叠加 `#define int long long` 让 `f[]`/`a[]` 各 8 MB。

**实测**（`resource.getrusage(RUSAGE_CHILDREN).ru_maxrss`，n=5 的极小输入）：

| 程序 | 峰值 RSS | 用时 |
| --- | ---: | ---: |
| Day7 A 赛时源码 | **65,912 KB（64.4 MB）** | 0.032 s |
| Day1 A 改写版（对照） | 10,260 KB | 0.002 s |

即**输入只有 5 个数却吃掉 64 MB**，6.4× 于正常程序。这是**仓库内可复现的同类工程常数实例**（Day7 A 的 `priority_queue` 数组）；转写 PDF `[G]` 里说的 `step` 百万级 `vector` 致 4 个 TLE 在仓库**没有对应源码**，两者不能混为一谈，该 `[G]` 保持 UNKNOWN。正确设计是「按实际用到的父节点开 `vector<vector<int>>`，或先离散化父节点再开桶」；本轮不改历史赛时源码，只留改写建议。

## 6. Day4 B 污染链的独立复算 `[E]`

`原始材料/T2_对拍污染链_非法generator_错oracle.md` 声称赛时 generator 合法率 `≈0.0282690368`。本轮用 `fractions.Fraction` 精确复算：

```
(1/10)·Σ_{n=1..10} (n/13)^n = 38971267793 / 1378584918490 ≈ 0.02826903680020397
```

与原文一致 → **97.17% 的随机输入不在题面定义域**。最小反例 `n=1, a=[1]`：真值 0（v 不能等于端点），错 oracle 输出 1。原文 50,069 个合法输入的三方穷举给出 false green 44.09% / false red 12.36%。本轮没有重跑那 50,069 组（属于已闭合证据，不重复劳动），只把**概率与最小反例**独立复算，作为 v2 验证器设计原则的输入：

> 真对拍必须闭合三层契约：`valid(input)` ∧ `oracle_verified(input)` ∧ `candidate_contract`。v2 因此先证明 oracle 本身（597,870 组穷举），再跑 candidate。
